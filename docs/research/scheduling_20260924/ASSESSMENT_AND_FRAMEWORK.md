# 局内调度量化：现有资料评估与量化框架（2026-09-24）

对照版本：统一版 #39，`claude/project-thread-fqyf7h` @ `25d7c2c`。只读，没有改代码。
范围：主线（F 羁绊、G 技能）与支线（V 宝物、点击进化、H 黑商 / 吞噬丹、物品栏、神器）穿插时怎么排先后。

## 结论

1. **机制描述够，数值不够。** 现有资料把"机制是什么"讲得很细：10 条 EX 合成链、卡族分支、宝物负面、黑商规则。但回答"这一步值不值"需要单价和收益数据，资料里几乎没有。机制库自己的 `unknown` 清单里就写着：F 抽卡单价、羁绊刷新单价、黑商刷新单价都未知，代码里的 40/60/80/100、400/300/350 都是待验证常量。
2. **缺的主要是"战力收益"这一端。** 成本端（木材、杀敌、技能点）HUD 大多能读到；收益端没有任何直接读数，脚本读不到攻击力、DPS 或战力值。所以 500、80% 这类阈值现在没法校准，不是资料没整理好，是没有衡量尺子。
3. **竞品帮不上调度的忙。** 三家竞品的资料集中在大厅、战后、图鉴和设置项。脚本1 的局内调度只看到一串布尔开关（`ASJJSFirst`、`AutoCard`、`AutoCleanInterval=5 分钟`、`ArtifactMode`），它自己也是按固定优先级和定时器排，没有量化模型。它 `AutoJob` 的局内主循环顺序和间隔还没人从反编译源码里拆出来，这一块值得本地补一次。
4. **长时间运行的兜底比调度成熟。** 单局 3600s 硬超时、主线 idle 看门狗、15s 无进展看门狗、每局新建房、incident 取证都已经有了。缺的是跨局健康统计（连跑 30 局的内存、句柄、耗时漂移）和"业务进度"看门狗：tick 在跑但主线、木材、卡组都不动的情况目前只由 15s 规则兜。
5. **建议路线：先装尺子，再调阈值。** 先定一个战力代理指标，再在 trace 里记齐"动作前后"的字段，本机跑 20–30 局 A/B，用数据反推阈值。GPT 负责案头调研和框架评审，本地 agent 负责补采只有本机才有的数据。两段提示词见同目录 `GPT_DESK_RESEARCH_PROMPT.md` 和 `LOCAL_DATA_COLLECTION_PROMPT.md`。

## 二、调度量化框架

### 2.1 核心思路

把每个可做的动作看成"花瓶颈资源换战力"，每个 tick 选"单位瓶颈资源换来的战力最多"的那个动作。

- **动作**：F 抽一张、刷新一次羁绊、G 点一次技能、拿宝物、点进化、用吞噬丹、黑商买丹、放神器、什么都不做（等资源）。
- **成本**：木材、杀敌数、技能点、刷新次数、羁绊栏格子，以及**时间**（点击和等弹窗占用的秒数）。
- **收益**：战力增量，但读不到，所以用代理指标（见 2.2）。
- **瓶颈资源**：此刻最紧的那一种。技能点不过期，影子价格接近 0；木材能转成羁绊，影子价格等于"下一次 F 抽的边际战力"；格子满时，格子的影子价格很高，所以吞噬丹值钱。

用这个框架重新表述现在的规则：

| 现在的规则 | 量化后的问题 |
|---|---|
| 木材 <500 先点技能 | 木材不够一次 F 时，F 的边际收益是 0，只剩技能能花。所以真正的门槛是"当前 F 抽价 + 刷新余量"，不是固定 500。需要的数据：F 抽价曲线 |
| 前期基础羁绊多拿、基础 80% 才开高级 | 比较"再拿一张基础"和"开始推高级组"两边的战力增量和回本时间。需要的数据：基础成型的战力跳变、高级组平均耗木和耗时、离 5-5 的剩余时间 |
| 羁绊栏 ≥8 格去找吞噬丹 | 吞噬丹的价值 = 它腾出的格子让下一张关键卡能进栏的概率 × 那张卡的价值。需要：格子满导致放弃关键卡的频率、丹的杀敌价、杀敌收入速率 |
| 黑商 440 预算 | 刷新 + 买丹的总杀敌价，以及刷出丹的概率。需要：刷新单价、丹价、每次刷新出现丹的概率 |
| 进化、神器、宝物的先后 | 这些动作不花木材，主要花时间。只要不和 F/G 抢同一个弹窗，就尽早做。需要：每个动作占用的秒数和收益 |

### 2.2 战力代理指标（从强到弱）

读不到战力，只能用结果间接反推。按可靠程度排序：

1. **主线推进速度**：每关从开始到通关的秒数（`_read_main_line_stage` 已能读关卡）。战力越强，通关越快。
2. **主线停滞**：停滞次数和时长（90s 判定已存在）。停滞说明战力不够。
3. **杀敌速率**：杀敌余额的变化加上黑商花掉的杀敌数，除以时间。
4. **挑战 Boss 击杀时间**：资源挑战、提前挑战、最终 Boss。
5. **局结果**：到 5-5 的时间、胜负、最终关卡。

一局只有一个结果，噪声大；关卡推进速度每局有几十个样本，更适合做校准。

### 2.3 trace 里要记的字段

现有 `SHUABAO_OBSERVE=1` 已经记了：每 tick 的木材、技能点、宝物数、计划目标和原因、阶段；每次选卡的槽位、族、稀有度、刷新次数、刷新价、决策。以下是缺的。

**A. 每 tick 状态（补）**
- `stage`（主线关卡 x-y）、`stage_started_at`
- `kill_balance`（杀敌余额）
- `bond_bar_occupancy`（羁绊栏占用格数）、`devour_pill_count`（丹数）
- `hero_level`（能读就读，读不出记 null）
- `base_bond_ratio`（基础羁绊完成度）、`active_advanced_group` 及其进度
- `main_line_stalled`（布尔）和停滞累计秒数

**B. 每个动作一条事件，必须带前后值**
- `action`（F / refresh / G / V / evolve / pill / merchant_buy / merchant_refresh / artifact / item_use）
- `wood_before` / `wood_after`、`kill_before` / `kill_after`、`skill_points_before` / `skill_points_after`
- `price_seen`（面板上能看到的价格文字，OCR 原文）
- `result`：拿到了什么（卡名、族、稀有度），或没拿到的原因
- `duration_s`：从发起到确认完成的秒数
- `confirmed`：只有业务确认后才为真（observed / requested / confirmed 三分）

有了前后值和价格原文，F 抽价曲线、刷新价、黑商价格就能从数据里直接算出来，不用猜。

**C. 结果和代理指标**
- 每关通关事件：`stage`、`clear_s`、当时的羁绊 / 技能 / 宝物摘要
- 每局汇总：到 5-5 的秒数、胜负、最终关、总木材收入 / 支出、各动作次数和耗时占比

**D. 支线事件**
- 进化：进化按钮出现时刻、点击时刻、选了哪个英雄、完成时刻
- 黑商：出现、打开、刷新（免费还是付费）、每个槽位的商品和价格、买了什么
- 神器：释放时刻、当时是否有 Boss
- 物品栏：每个格子的物品类别、使用时刻

**E. 长跑健康（每局一行）**
- 进程内存、句柄数、单局耗时、OCR 平均延迟、看门狗触发次数、incident 数

### 2.4 怎么反推阈值

1. **先从 B 类事件直接算单价**：F 抽价曲线、羁绊刷新价、黑商价格。这一步不需要实验，正常跑几局就有。
2. **再做 A/B**：一次只改一个阈值（例如 500 改成"F 抽价 + 40"，或 80% 改成 60% / 100%），同一英雄、同一难度，每组 20–30 局，比较主线推进速度和到 5-5 的时间。
3. **也可以离线做反事实**：用 observe 日志统计"当时 F 和 G 都可选、实际选了 G"之后 60 秒内关卡推进速度，和选 F 的情况比较。这不需要额外跑局，但会受当时局面影响，只能做方向性参考。
4. 结果只作设计输入。改默认值要单独立项、单独提交、过门禁，并在交接文档里记录证据。
