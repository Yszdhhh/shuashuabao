> 数值来源等级统一为：`live`（仓库实机截图/录屏/trace）、`guide`（公开攻略）、`inferred`（本文推断/实验设计）、`none`（未找到可信来源）。实现常量本身不是机制证据。

# 结论

1. **目前最该做的不是再挑一组“更聪明的固定阈值”，而是把固定阈值降级成待校准参数。** 公开攻略能证明“节奏随主线阶段、卡池、卡槽和当前构筑而变化”，但没有找到可信资料能给出 F 抽卡完整木材单价曲线、羁绊刷新完整单价、吞噬丹固定杀敌价、黑商付费刷新固定价或吞噬丹出现概率。因此 `500/1000/300/80%/480s/2 次/8 格/440/技能积压 4` 都不应被外部攻略“认证”。
2. **我方“单位瓶颈资源换战力”方向正确，但不能直接做成一个标量 ROI 排序器。** 木材、杀敌数、技能点、卡槽和时间不可稳定换算；合成链有延迟回报和卡池稀释；刷新会改变后续抽样分布；格子接近满时吞噬丹的边际价值会突增。低成本方案应是：**硬约束/Owner 规则 → 事务闭环 → 可行动作 Pareto 前沿 → 上下文边际价值（shadow price）→ 防饿死**，而不是把所有资源换成一个分数。
3. **最值得优先采的数据只有四类**：F 每次真实成本与刷新成本、每个 stage 的通关耗时、杀敌净收入速率、卡槽“差一张/满槽/需要丹”的事件。只要这四类对齐到动作前后，就已经能校准 500、1000、300、8 格、440 和刷新 2 次的大部分问题。
4. **竞品没有展示出比我方更先进的量化调度器。** GameScript 可确认的是固定优先开关、定时器和模式参数（如 `ASJJSFirst`、`AutoCleanInterval=5` 分钟、`GameTimeOut=15` 分钟、`DevelopTime`、`ArtifactDelay`）；脚本3 有 `gamble_min_wood=3000` 和较好的刷新否定证据，但同样是固定门槛。值得借鉴的是**显式事务、定时任务、失败否定证据和业务进度计量**，不是它们的常量。
5. **建议本机实验预算 48 局（`inferred`，小于任务上限 60 局）**：8 局只观测基线 + 16 局木材/F 调度 A/B + 12 局基础/高级卡组门槛 A/B + 12 局卡槽/黑商 A/B。每一组固定英雄、难度、版本和局外配置，交替运行 A/B，主指标用“到 5-5 时间/最终 stage、stage 通关秒数、主线停滞总时长”，资源指标只作解释变量。
6. **长跑 8–10 小时的第一优先级不是自动恢复，而是跨局健康统计和业务进度看门狗。** 发现“tick 还在跑但 stage、木材、杀敌、卡组长期都不变”时应该取证、结束当前安全事务、标记该局异常；不要连按 ESC，也不要盲点坐标。

# B. 竞品调度思路

## B1. GameScript：能确认的事实 vs 推断

| 层 | 仓库竞品文档可确认 | 等级 | 本文推断 |
|---|---|---|---|
| 主循环形态 | `AutoJob.Run()` 下挂大厅、局内、战后；存在 `DevelopTime`、`DevelopPriority`、`GameTimeOut=15` 分钟 | 文档原文 | 更像“状态 + 定时任务”的轮询器，而非统一效用函数 |
| 羁绊/技能 | `AutoCard`、`Skills`、`Cards`、`SingleSelectedSkill`、`ASJJSFirst` 及多种增伤优先开关 | 文档原文 | 面板内应先走硬优先标签，再走普通白名单；但具体每 tick 次序目前不能确认 |
| 背包 | `AutoCleanInterval=5` 分钟 | 文档原文 | 定时器到了才插入，不参与每 tick 的资源 ROI |
| 神器 | `ArtifactMode` + `ArtifactDelay` | 文档原文 | 定时/冷却驱动，而不是资源驱动 |
| 赌木 | `AutoGamblingTime` | 文档原文 | 到时触发专项流程 |
| 发育/挑战 | `DevelopTime`、`DevelopPriority` | 文档原文 | 先发育多少秒、再推进挑战，是阶段式调度 |
| 超时 | `GameTimeOut=15` 分钟 | 文档原文 | 超时保护在业务策略之外，是独立 watchdog |
| 黑商 | 现有 Settings 映射没有完整商品 EV/刷新概率模型 | 文档原文 | 暂无证据证明它会按“每点杀敌的边际战力”排序 |

**结论**：GameScript 可以借鉴的是“**硬优先级 + 定时器 + 模式分层 + watchdog**”；不能证明它有更先进的经济模型。当前本地补采任务去反编译 `AutoJob` / `CardGroup` 的真实循环顺序是必要的，在那份结果回来前不要把上面的推断写成事实。

## B2. 脚本3：最有价值的是工程语义，不是数值

竞品3 可确认 `gamble_min_wood=3000`（`inferred/competitor-config`，只是对方默认），以及刷新前后像素指纹、三态面板、失败返回安全哨兵等做法。**3000 不能迁移为我方阈值**；值得迁移的思想是：

- 刷新前后要有“变化/无变化/无法判断”三态，而不是二态；
- 采样失败不能等价为“没有变化”；
- 同一商品/卡位多次无变化应停止烧资源并落原因；
- 面板动画/坏帧时 `WAIT`，不猜。

## B3. 对我方的可借鉴结论

值得借鉴：
1. **事务优先**：已经打开的面板/正在等待 mutation 的动作必须先闭环。
2. **定时动作独立调度**：神器、清背包、免费黑商刷新等适合 deadline/timer，不应塞进 F/G 的同一收益函数。
3. **硬质变点优先**：像 `ASJJSFirst` 这种“拿到后改变技能形态”的卡，应作为 breakpoint，不是普通技能点。
4. **失败否定证据**：刷新是否生效、购买是否成功必须看业务 postcondition。

不值得照抄：
1. `AutoCleanInterval=5`、`GameTimeOut=15`、`gamble_min_wood=3000` 这类常量本身；
2. 固定坐标和超时后盲点；
3. “配置项越多=策略越好”的思路。

# C. 量化调度框架评审

## C1. “单位瓶颈资源换战力”框架的主要漏洞

1. **跨币种不可稳定标量化**：1 木材、1 杀敌、1 技能点、1 卡槽和 1 秒在不同阶段的价值不同。技能点不过期时影子价格很低，但接近 23/36/40/46 等 breakpoint 时会突然升高（`guide`）。
2. **回报延迟**：高级组可能连续花木几分钟才兑现，若只看下一 tick 的 stage 秒数，会系统性偏爱短期动作。
3. **合成周期/卡池稀释**：拿一张启动卡可能把新卡加入池，短期没有战力但会改变未来抽卡分布；刷新也会改变未来样本。
4. **卡槽是非线性约束**：9/10 与 10/10 不是连续差异；差一张合成时，一个空槽/吞噬丹的价值可能远高于平时。
5. **随机性强**：同一策略因为抽卡、黑商、宝物、怪物进度不同会产生大方差；单局比较会误判。
6. **代理指标受混杂**：stage 通关快可能来自英雄、宝石、BOSS词条或临时神器，而不一定是刚刚那次 F/G。
7. **幸存者偏差**：只统计“成型成功”的高级组会高估高级组价值，应同时计入中途没成型的沉没成本。
8. **刷新具有期权价值**：把刷新简单记成“花木材换一组三选”会遗漏“保留刷新次数到更窄卡池阶段”的价值。

## C2. 低成本优先的形式化方法

| 方法 | 推荐度 | 数据量（`inferred`） | 优点 | 风险 |
|---|---|---:|---|---|
| **硬约束 + Pareto 前沿 + 参数扫描** | 第一优先 | 20–30 局起步 | 与现有 `solo_scheduler.py` 的不可跨币种比较天然一致；实现最小 | 不能自动学习长期回报 |
| **上下文 shadow price / 边际价值表** | 第一优先 | 30–50 局 | 把“木材价值、格子价值、技能点价值”按 stage/卡组进度分段 | 需要足够覆盖各状态 |
| **事件研究（before/after stage time）** | 高 | 每类动作约 20+ 事件 | 适合估计进化、质变技能、完成羁绊后的即时收益 | 易被同时发生的动作混杂 |
| **简单双臂 A/B + blocked randomization** | 高 | 每对策略 12–16 局 | 最容易解释、可在本机直接执行 | 成本较高，一次只能校准少数参数 |
| **Contextual bandit** | 中后期 | 100+ 局更合理 | 能学“什么状态下选 F/G/黑商” | 当前数据量和动作安全边界不足 |
| **完整 RL / reward shaping** | 暂不推荐 | 数百到数千局 | 理论上能处理长期回报 | 真实环境样本昂贵，且错误动作有真实代价 |

推荐形式：

```text
Owner/安全硬约束
    ↓
未闭环事务优先
    ↓
合法候选集合
    ↓
不同币种先保留为 Pareto 前沿（不强换算）
    ↓
用 stage、卡组进度、槽位自由度、breakpoint 给“上下文边际价值”
    ↓
同级时才用 anti-starvation / current_chain 决胜
```

这比“每 tick 统一算一个 ROI 最大值”更适合当前数据和 fail-closed 约束。

## C3. 九个现有阈值怎么校准

| 阈值 | 当前值 | 需要数据 | 校准方法 | 何时有资格改 |
|---|---:|---|---|---|
| 技能优先木材线 | 500 | 当前 F 下一抽真实价格、木材净流入率、技能是否临近 breakpoint | 用“能否支付下一次 F + 预留一次刷新/现金流恢复时间”替代固定值；先 shadow 回放 | 至少 10 局覆盖低木材窗口（`inferred`） |
| 高木材线 | 1000 | F 连抽真实边际成本、stage 停滞、木材溢出时间 | 比较“继续 F”与“转 G/支线后 60–120s stage 速度” | A/B 16 局后 |
| 低木材每轮 1 张 | 300 | 下一抽价格、木材恢复到可再次抽所需时间 | 将门槛改写为“现金 runway”，而不是 300 | 能准确读 F price 后 |
| 基础完成比例 | 80% | 基础各节点完成时间、完成前后 stage 秒数、高级组起步后的时间 | 70/80/90% 不宜一次全跑；先比较 current 80% vs “高价值基础节点完成即开放高级” | 12 局 A/B 后 |
| 高级兜底 | 480s | 不同难度到 5-5 的时间分布、首次高级组启动时间 | 用“预计剩余可兑现时间”替代固定 480s；先按 stage 分层 | 至少 20 局 baseline |
| 每组刷新上限 | 2 | 每次 refresh 后命中目标概率、每次真实木材价、卡池宽度 | 计算第 1/2/3 次 refresh 的经验边际命中率与成本；当边际收益低于保留木材的价值停止 | 每组累计 ≥30 次 refresh 事件（`inferred`） |
| 8/10 格找丹 | 8 | occupancy、下一关键卡到达概率、因满槽错失卡次数、丹持有数 | 改成“自由度 = 空槽 + 丹”；当预计下一关键卡需要的自由度超过当前自由度时才提高 merchant 优先级 | 至少 10 次满槽/近满槽事件 |
| 黑商预算 | 440 | free/paid refresh 价、丹价、merchant level、刷出丹概率 | `EV cost = paid_refresh_cost / P(pill per refresh) + pill_price`；免费刷新单列 0 边际刷新成本 | 至少 50 次黑商商品曝光/等级（`inferred`） |
| 技能积压 | 4 | 技能点、技能当前等级、下一 breakpoint 距离、stage stall | 从“点数数量”改成“距质变点还差几张/是否正在 stall”；普通积压不应自动产生紧迫性 | skill breakpoint 表 + 10 局对齐 trace |

**核心判断**：最先应该淘汰的是“技能积压=紧急”的抽象，而不是先把 4 改成 3 或 5。公开攻略已经显示技能价值高度分段；普通积压和“差一张急速抽箭/技能等级质变”不是同一类状态。

# D. 本机可执行实验设计

## D1. 总预算

建议 **48 局（`inferred`）**，全部单人、固定同一游戏版本；不混蹭车。若某阶段发现强事故，停止该阶段，不为了凑样本继续跑。

| 阶段 | 局数 | 目的 |
|---|---:|---|
| D0 观测基线 | 8 | 建立 stage time、wood rate、kill rate、事件完整性 |
| D1 木材/F 调度 | 16 | current 固定阈值 vs price/runway 上下文策略 |
| D2 基础→高级切换 | 12 | current 80%/480s vs 节点+预计兑现时间策略 |
| D3 卡槽/黑商 | 12 | current 8 格/固定预算 vs freedom/经验概率策略 |
| 合计 | 48 | 留 12 局余量给复测/事故重跑，不超过 60 |

## D2. 控制变量

每一个 A/B block 都固定：
- 游戏版本 / 地图版本；
- 章节与难度；
- 英雄；
- 局外宝石、珍藏、存档、声望、神器配置；
- choice preset / 高级卡组选项；
- 是否自动主线、是否提前挑战；
- 分辨率与 OCR 环境。

运行顺序使用 **ABBA / BAAB** 交替（`inferred`），不要先连续跑完 A 再跑 B，避免机器温度、网络时段和人工疲劳造成时间趋势偏差。

## D3. 每局必记指标

主指标：
1. `time_to_5_5`；如果没到 5-5，记录终止时 `stage`；
2. 各 stage `clear_time_s` 的中位数和 P75；
3. `main_line_stall_total_s` 与 stall 次数；
4. 胜负 / 是否因 3600s hard timeout 终止。

资源解释指标：
- `wood_income_rate`（扣除已知消费后的估计）；
- `kill_income_rate`；
- 每个 F draw / refresh 的真实 cost；
- 技能点峰值与距 breakpoint；
- 每个高级组 start/end/time/cost；
- `bond_bar_occupancy`、`devour_pill_count`；
- 因卡槽不够而放弃/替换关键卡的次数；
- merchant refresh 次数、free/paid、pill exposure 和 pill purchase。

安全/可靠性指标：
- UNKNOWN/WAIT 占比；
- transaction timeout；
- OCR latency P50/P95；
- 重复点击/无 mutation 次数；
- incident 数。

## D4. 判定方法

不建议只看“平均通关快了几分钟”。

- 连续指标：报告中位数、IQR、bootstrap 95% CI（`inferred`）。
- 完成率：报告到 5-5 的比例和 Wilson CI（`inferred`）。
- stage 级数据：同一局内多个 stage 不是独立样本，分析时按“局”为 cluster，避免伪扩大样本。
- **实用显著性门槛先于统计显著性**：例如策略若只快 1–2%，但 UNKNOWN/事故上升，则不采纳。建议预先定义“至少 8% 的 time_to_5_5 改善或 ≥20% stall 降低，且安全指标不劣化”为值得进一步验证的量级（`inferred`，不是生产阈值）。
- 12–16 局/组通常不足以证明小效应；如果 CI 很宽，结论应是“未定”，不是“无差异”。

## D5. D0 先验证日志是否够用

在任何行为 A/B 之前，先用 8 局只观测确认以下链路能闭环：
`action requested → action confirmed → resource before/after → stage before/after`。

缺字段时先补观测设计，不要急着改策略。尤其必须区分：
- F draw vs bond refresh；
- merchant free refresh vs paid refresh；
- “商品没出现” vs “没读到”；
- “点击成功” vs “购买/选卡业务成功”。

# E. 连续跑 8–10 小时的失败模式与检测信号

| 失败模式 | 建议检测信号 | 处理原则 |
|---|---|---|
| tick 活着但业务不推进 | stage、wood、kill、bond progress 在较长窗口内全部不变；同时没有合法等待原因 | 生成 incident；结束当前安全事务；该局标异常，不连按 ESC |
| OCR worker 冷启动/退化 | OCR latency P95 上升、timeout/empty result 比例持续升高 | 重启只读 OCR worker 或结束该局；不要把空 OCR 当 0 |
| 内存/句柄泄漏 | 每局结束记录 RSS、handle count；连续多局单调上升 | 跨局阈值报警；优先每局新房/进程重建而不是局内盲恢复 |
| 前景/窗口身份漂移 | HWND/title/viewport identity 与期望冲突 | 零输入；重新确认窗口身份 |
| 模态弹窗长期覆盖 | modal identity 连续多帧稳定存在但对应事务没有 mutation | 用该 modal 的语义动作；未知 modal 只取证 |
| 面板刷新失效 | refresh 前后 panel fingerprint 无变化且 fresh frame 已确认 | 停止继续烧刷新；记录“no effect” |
| 黑商烧杀敌但没产出 | paid refresh 计数上升而 pill exposure 长窗口为 0 | 暂停付费刷新；保留统计，不推断“商店坏了” |
| 卡槽死锁 | occupancy 10/10、pill=0、关键卡连续出现且无法合法收入 | 提升 merchant/pill 事务优先；仍无证据则 WAIT/ABANDON |
| 主线难度失配 | stage stall 累计上升、挑战失败重复、清场/降级机制触发 | 走已有降级/失败证据链，不加固定坐标逃生 |
| 网络/平台断线 | 真实断线/平台 modal anchor；窗口帧不再是游戏 HUD | fail-closed + incident；没有真实断线证据时不自动猜按钮 |
| 跨局状态污染 | 新一局开始后仍看到上一局 round_id/ledger/timer | 立即阻断自动输入并报告，作为高优先级架构事故 |
| 性能热漂移 | tick interval、capture/OCR latency、CPU/RSS 随局数漂移 | 每局健康表 + 趋势报警 |
| 通知链自身故障 | incident 已产生但通知 webhook 未确认 | 通知失败不得影响本地 fail-closed；落盘重试队列 |

### 跨局健康表最小字段

建议每局结束写一行（`inferred`）：
`round_id, start/end, result, final_stage, time_to_5_5, stall_s, incidents, rss_mb, handles, capture_p95_ms, ocr_p95_ms, unknown_ratio, paid_merchant_refreshes, pill_exposures, fatal_reason`。

业务进度 watchdog 不应只看“15 秒有没有动作”，而应看“**有动作但有没有业务结果**”。一个可实现的研究口径是：当 stage、资源、已确认卡组 ledger 在一个长窗口都没有变化，且不存在明确等待中的定时收益/挑战战斗/已知面板事务时，判为“业务无进展”。具体窗口长度先从历史正常局 P99 推导，本文不拍固定秒数。
