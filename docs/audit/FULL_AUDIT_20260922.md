## 1. 一页结论

**当前最重要的判断：影子实现可保留为实验代码，但尚不能作为已完成 §11 契约的动态调度器，也不能把它目前的分歧率、不可比率当成可信的策略优劣结论。**问题不是少一个权重，而是候选合法性、未知信息处理、比较顺序、服务时钟、记录配对和测试证明范围尚未闭合。

线上单人仍是 **固定环 + 局部强抢占 + 机会式支线**，不是统一的前期/中期/后期调度。前期默认从 F 起步，不等于 `round1_must` 全部打满；基础 80% 实际是家族至少出现一张。技能 `>=8` 强抢占，以及另一层 `>=4` / 停滞时 `>=1` 的倾向，仍与 Owner 的技能零时序机会成本方向冲突。宝物确有一次让位例外，但只绕过高木材 F 优先，不能绕过后面的技能抢占，因而没有全局不饿死保证。

**生产消费风险仍在：**单人黑商读不到杀敌余额时继续授权购买。该风险在第一批影子交接中被明确保留为对照差异；本次没有替 Owner 改掉。它是 P0 级风险路径，不是本次观察到的一笔实际错误扣费。

**已修复三个有明确反例、且不改变线上游戏动作的问题：**

1. 影子消费判断允许非有限/非法数值，同币种多笔成本重复使用同一余额。
2. 影子持有账目缺失或读取异常被写成 `observed([])`，把“读不到”冒充“确认没有”。
3. 行为比较工具在两边失败、通过数不同等情况下仍可能返回 0，制造假绿。

**不要继续报成当前缺陷的旧结论：**单人黑商范围已经恢复“吞噬丹 → 木材 → 2/5 折”；单人 EX 宝物跨品质优先已经恢复；生命 canonical catalog 已是 need=3；单人定时 F4 已被禁用。研究草案中 D5/D8/D13 和部分 D7 描述落后于当前基线。

## 3. 按严重度排列的问题

### A01 · P0 风险 · 单人黑商未知余额仍授予消费许可【未修；Owner 决策】

**位置：**`mediator.py:6280–6460`，黑商预算判断及购买入口；`docs/research/20260922/handoff/L1_SOLO_SHADOW_SCHEDULER_BATCH1_20260922.md` §4。

**现象与证据：**杀敌余额为 None 时，乘客模式拒绝，单人模式返回允许。源码分支确定；本次实机错误扣费样本 n=0。第一批影子任务明确要求保留线上这条路径，并让影子按 BALANCE_UNKNOWN 拒绝，以测量差异。

**影响：**余额未知仍可能发购买请求；400/300 等代码估价也不是商品实价证明。实际钱不足可能由游戏拒绝，但这不能作为脚本消费授权纪律。

**建议：**Owner 单列批准将单人消费入口改为未知余额拒绝；复用已有短暂预算退避并让其他链继续，不能把全局停在商店。分别记录“价格来源”“余额新鲜度”“动作请求”“货物确认”。不要以三次盲点商品无变化来代替购买前授权。**本 PR 未改变此既有对照规则。**

### A02 · P1 · 技能积压强抢占与 V/支线服务不闭合【未修；Owner 决策】

**位置：**`mediator.py:4510–4630`，`_skill_backlog_force`、`_solo_plan_panel`；`config/game_mechanics_kb.json:204–232`。

**现象：**技能 >=8 在高木材 F 逻辑之前抢占；之后还有默认 >=4、停滞时 >=1 的技能分支。V 例外只包在高木材羁绊分支内，技能分支没有对称让位。被抢占时原 cycle step 并不必然得到服务。

**证据：**源码分支与 KB Owner 口述冲突。KB 记载 9 局中 6 局该规则影响至少 40% 的决策；示例 20260918_210044 为 22 次计划、13 羁绊/9 技能抢占。这是研究转述，本次未重算。

**影响：**“技能未花完”被当成紧迫性；持续满足条件时，V 和后续装备/黑商等访问可能被推迟。不能反过来说所有宝物都会饿死：已出现的自然宝物面板先走面板 FSM。

**建议：**线上迁移时消除纯积压数的紧急语义，不仅检查 >=8。失败事件也不能直接映射为技能唯一解；只比较有合法机会与效果依据的候选。记录每类合法机会最长等待及本次实际服务。**不新增阈值，本 PR 未改线上抢占。**

### A03 · P1 · 木材档位、基础完成与阶段语义混用【未修；Owner 决策】

**位置：**`mediator.py:3415–3433`、`4260–4785`；`choice_policy.py:1435–1565`。

**现象：**300/1000 同时影响 F 可推进、优先级及访问预算；Owner <500 口述是另一种节奏建议。基础 80% 是“家族至少有一张”，不是 `round1_must` 每组 need 打满；约 480 秒的高级解锁兜底也不是由实际关卡进入中期。

**证据：**`completed = sum(any(...))` 与 `ceil(len(bases)*ratio)`；高级解锁同时可由 elapsed 触发。源码事实，不以攻略时点当实机阶段。

**影响：**“低于某余额不能 F”会排除实际可支付的机会；“基础齐了”日志容易被理解成套装完成；稳定高木材本身不能证明当前有值得插队的 F 候选。

**建议：**区分已展示目标成本、整条短链预算、服务优先级、访问保护预算四种量。保留保护超时，不把 D10 简化成再加一个 500 档；D12 明确改文档语义。**本 PR 不改这些参数。**

### A04 · P1 · 影子合法性未守住页面与后续购买信息边界【未修】

**位置：**`solo_scheduler.py:290–478`、`481–489`、`502–530`。

**现象：**未知 panel/transaction 可以进入候选比较；未知 G/V 也生成 legal READ 候选；已知刷新价但未知后续抽卡/目标价时仍可能推荐刷新。开 G/V、现有面板读取、消耗领取次数的语义没有完整分开。

**证据：**标量反例 n=2：未知页面 + 技能角标 1 得到 RECOMMEND；木材 100、刷新 40、后续价 unknown、G/V=0 得到 bond_refresh。没有真实输入，证明的是推荐契约缺口。

**影响：**影子会把未授权的交互面、没有可解释短链预算的刷新计作正常建议，降低不可比/观察比例。

**建议：**A 层必须显式携带已授权 surface；B 层区分 read/open/claim，缺关键后续价格不得把刷新链写成有预算保证的推进。保留不依赖缺失字段的候选，而非全局停机。

### A05 · P1 · 影子支配与公平服务被隐性排序替代【未修】

**位置：**`solo_scheduler.py:252–279`、`551–668`。

**现象：**D 只按同 goal、币种集合、硬编码 evidence/cash-in ordinal 比较，没有切换成本；free/paid 分支可能把整组 paid 移除；E 以兑现序号、证据序号、等待时间、action_id 排序，`goal_preference` 未参与约束。同“merchant_spend”目标名也不证明不同商品收益等价。

**证据：**标量反例：G 角标 unknown、等待 1000；V=2 observed、等待 10，仍按 anti-starvation 选 G。公平分支比较 `oldest.evidence_rank <= second.evidence_rank`，没有证明它们是等价机会。

**影响：**未服务时间可放大弱证据候选；字典序/列表首项成为未声明的偏好。代码没有设币种汇率，这是优点，但不等于所有跨币种候选始终被保留为不可比。

**建议：**将可比维度与未知明确建模；未知不能证明“不更差”。公平服务只在已合法、收益/目标可比的等价组内进行，保持真实有效链。不能证明优劣时保留不可比 + REVIEW_REQUIRED，不靠名称强选。被支配、不可比、让位必须分别记录，不能把 Pareto frontier 的其他项标 DOMINATED_IN_FRONT。

### A06 · P1 · §11.3F 被多候选提前返回绕过【未修】

**位置：**`solo_scheduler.py:575–668`、`683–718`。

**现象：**跨币种和多候选路径提前返回，只有单一 frontier 才执行 F。末段安全入口过滤还含 `or True`；没有入口时的 `indep[0]` 又引入列表优先级。

**建议：**D/E 产生暂定选择或不可比集合，统一经过 F 再返回；入口必须与缺口匹配。不要通过减少 unknown 样本或给它们默认值来提高推荐率。

### A07 · P1 · 快照新鲜度、价格来源和服务时钟失真【部分相关问题另见 A08；本项未修】

**位置：**`solo_shadow.py:92–247`、`250–291`；`solo_scheduler.py:295–319`；`mediator.py:1180–1194`、`4419–4432`。

**现象：**非空的 sticky G/V 被记为 observed，却没有原观测帧/时间；只在 None 时标 sticky_or_unread。模型价以 Fact.observed 表达、仅 source 带 model；picks 缺失通过 `or 0` 推出首抽价。展示卡模型价在构造 chosen Cost 时又写成 model_derived=False。服务等待用上次“开面板尝试”的时间，而 0 表示本局从未打开，被换算成从 epoch 起等待。

**证据：**当前字段赋值和初始化；标量展示卡 source=model:test 时，输出 Cost.model_derived=False。n=1 反例。没有把这些记录宣称为逐帧真实观测。

**建议：**保存 value/state/source/observed_at/frame-or-generation/round_id；sticky 继承原时间而非刷新成 observed-now；推算价保留 model-derived，未知 picks 不生成确定价；区分 last_attempt 与 last_confirmed_service，从本局可证的起点计时。现有日志缺字段的样本标 unknown，不回填猜测。

### A10 · P1 · 比较工具可假绿；统计相同仍不是行为不变【假绿已修，行为证明仍未完成】

**位置：**原 `tools/compare_solo_shadow_behavior.py:18–78`。

**现象：**原返回值在比较失败后还允许“只要双方文本有 passed 就返回 0”；同样失败或错误摘要也可能被判相同。未比较动作序列，未断言 shadow hook 实际进入。

**修复：**两侧 exit=0、可解析正通过数、无 failed/error/xpass、计数相同才返回 0；保存 stderr，约束子进程等待；明确输出 NOT_BEHAVIOR_PROOF。11 个反例由全失败转全通过，提交 `559e1ce`。

**剩余建议：**用正式主线调用和已有真实资产测试记录输入网关动作序列、关键业务状态、shadow hook 调用次数及异常路径；两组 pytest 汇总数相同不能代替这些断言。

### A11 · P1 · 非法数值与同币种预算被错误授权【已修】

**位置：**原 `solo_scheduler.py:58–70`、`114–148`、`236–279`。

**现象：**NaN/Infinity/负数等可绕过比较，巨大整数转换会异常；多笔同币种费用逐笔比较同一个余额，`cost_of` 又只取第一笔。

## 4. 调度逻辑专章：现在一个 tick 到底怎样执行

### 4.1 实际主线顺序

以下是已读取的 MAIN_LINE 关键路径，省略平台登录/找房完整状态机；任何阶段触发 return，本 tick 后续项均不执行。依据 `mediator.py:16698–16880,17520–18145,18145–18310` 与 `runtime_mediator.py:210–320`。

```text
Runtime._tick_main_line（LIVE）
  -> HUD/watchdog 观察
  -> Core._tick_main_line
       -> observe + shadow hook（在本帧业务信号刷新之前）
       -> 已有局尾/战后/退出与恢复等门禁
       -> 单交互面仲裁
            CONFLICT -> 零输入；稳定窗后仅按已知自开面板/词缀收敛
            装备词缀 / 英雄选择 / 中央选卡 -> 对应处理，通常 return
            商店 / 恢复 -> 对应 FSM
       -> 已验证局尾入口 / 战后转场处理
       -> 当前 HUD / 错页 / 指针等保护
       -> 配置的 Boss 入口、自动任务确认、四挑战确认、英雄焦点 F1
       -> 已授权 HUD 且无事务：提前挑战 / TQTZ
       -> 主线读数或 close-after-5-5 helper（配置分流，不重复抢 OCR）
       -> 单人定时 F4 路径实际不发输入
       -> 可选开波前 20s 主动操作保护（自然面板已在上面处理）
       -> 自开紧凑候选条 / 装备 pending 收口
       -> 进化反馈、英雄卡选择锁（未完成不切去其他业务）
       -> HUD 机会式：神器 -> 吞噬丹（守卫恒 False）-> 溢出拾取
       -> 主动 F/G/V：_solo_plan_panel -> _maybe_open_choice_panel
       -> 前项没有动作时的 HUD 机会式：武器1号格 -> 进化 -> 英雄卡 -> 黑商
       -> 显式 cycle step：artifact/evolve/equipment/public_bag/pickup/merchant
       -> 末端活性步进（仅内部 cycle，不盲发 ESC）
  -> LIVE watchdog：仅遥测，无新游戏输入
```

默认单人环是：

```text
F 羁绊 -> G 技能 -> F 羁绊 -> G 技能 -> V 宝物
 -> 点击进化 -> 装备 -> 拾取/物品栏 -> 黑商 -> 神器 -> 重复
```

`public_bag` 有 handler，但不在这条默认 solo 环中。不能因函数存在就宣称单人必定执行公共背包清包。蹭车有自己的环，不应套用这张单人顺序图。

### 4.2 谁能抢占谁，现有阈值是什么

| 层次 | 当前规则 | 实际意义 |
|---|---|---|
| 面板/事务 | 自开候选条、中央卡面、进化反馈/英雄选择、equipment pending 先收口 | 不能仅因技能点变多就打断进行中的事务；但必须核验所有完成标记的后置条件 |

| V 例外 | 当前 cycle=treasure 且 V 未知或 >0 时，高木材 F 不抢 | 只绕过 F 分支，不能绕过前后 G 抢占 |
| 次级 G | 默认 backlog>=4；主线停滞时门槛降为1 | 同关90s/失败标签不等于已经证明技能是解法 |

### 4.3 前期怎么拿：直接回答

**羁绊启动与门卡：默认先到 F，但没有统一的“所有启动卡/门卡见则抢”。**进入 F 之后，仍先受合法性、配置、卡位/合成、基础/高级组限制，再按 must-take、差一张成型、已持有合成、预设顺序等规则选择。`_match_bond_preset` 用预设顺序、品质、槽位作确定性排序（`choice_policy.py:1606–1622`），不是根据“启动早一分钟多多少成长”比较。

**`round1_must` 不保证打满。**攻略/默认策略的阶段名单不等于运行时已经设置完成屏障；基础 80% 只统计家族出现过。一个家族拿到一张就可能贡献完成计数，和 need=3/4 的满套不是一个量；高级组也可按 elapsed 兜底解锁。不能把“基础门槛通过”记成“前期构筑完成”。

**技能什么时候上车：**除自然技能面板外，G 本就在环内出现两次；积压规则会提前抢占。F 不可推进/暂停、G 有机会等情况下也可转 G。当前不是“先把所有羁绊成长启动完，再统一点技能”。Owner 的“技能点不消失”是机制/策略方向，不能反推“任何时候点技能都没有战斗机会价值”；需要真实可学且匹配的技能机会，而不是仅用角标计数。

**宝物什么时候插入：**已经显示的可信中央宝物面板优先走面板 FSM，安全过滤后按 EX/品质/预设选择；尚未打开 V 时，依赖轮换或计划让位。有 V 次数、页面已有安全选项、能补构筑，应当获得服务，但当前规划器并没有完整的“能补当前构筑”候选信息，更没有覆盖持续 G 抢占的公平保证。故答案是：**自然面板能插入，主动领取仍可能长期被 F/G 延后；不能宣称已经证明不饿死。**

### 4.4 中期、后期与失败墙

**中期：**系统仍跑同一个环。基础家族比例、elapsed、高级组和 confirmed 卡链会改变 F 内部选卡；高木材继续加大 F 访问预算。武器、进化、英雄卡可在机会位置执行，不必机械等待整个环结束，但会被前置事务/主线 return 和高木材 core-development 保持条件挡住。没有统一的关卡进度驱动调度。

**后期/Boss：**可信局尾入口、提前挑战/配置 Boss 路径可能在普通拿卡前处理；不会自然切换成一套完整的“后期只拿即时战力”候选系统。5-5 后关闭自动任务已有配置路径，但 A13 的 requested/done 仍需修。Boss 双帧无卡保持 done+unconfirmed 的 Owner 裁定不应改动，本 PR 没有改它，也没有用该规则证明 Boss 已受理。

**失败墙：**真实失败文字或同关90s会改变旧逻辑的技能倾向；同关时长没有剔除面板、不可见或非有效战斗时间。影子不能把这个信号翻译成缺输出/缺生存，更不能新增效果映射表。G1 真信号未就绪时保持 OBSERVE/不可比。

研究草案的“0–5分钟/5分钟到5-5”等是 n=1–3 的案例窗口，不是本次证明的统一分段阈值。hitch 45 段中位589s不能作为完整单人局时长。
