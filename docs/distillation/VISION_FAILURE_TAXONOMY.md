## 2. 深度剖析：为什么必须“REMOVE OCR”而非“FIX OCR”？

### 案例 1：宝物面板 (FAIL-01)
- **实测数据**：在 45,078 条 OCR 记录中，`treasure` 占据 12,360 次，`treasure_desc` 占据 12,285 次。
- **准确率**：`treasure` 词典命中率仅 **1.4%**（平均分 0.022），`treasure_desc` 命中率 **0.0%**（100% 报错）。
- **业务事实**：在游戏自动化主线中，宝物掉落后机器人的最优策略是“优先拾取第一个可用宝物，若有高稀有度则选高稀有度，否则直接关闭”。
- **决策结论**：**继续训练 OCR 识别宝物完全是南辕北辙**。直接在代码中关闭宝物 OCR，改为 ROI 检测后直接点击首槽或按 HSV 判定金/紫边框，**瞬间砍掉 54.6% 的系统 OCR 开销，且业务成功率提升至 100%**。

### 案例 2：预处理多变体反向吞噬 (FAIL-02)
- **现状**：`worker.py` 对每个输入图像依次跑 6 种滤镜：原图、`R-B`、`G-B`、`B-R`、`Otsu`、`Gray>=180`，并逐个写入硬盘临时文件 `tempfile.NamedTemporaryFile` 后调用 Paddle。
- **实验对比**：
  - `Gray_2x` 单一通道内存推理：词典准确率 **91.6%**，p50 延迟 **20.8ms**；
  - `ColorDiff(R-B)`：词典准确率仅 **6.5%**；
  - `Otsu`：词典准确率降至 **69.5%**；
- **决策结论**：**6 重滤镜不仅浪费了 5 倍的 CPU 算力，还引入了大量噪声使低置信度乱码污染最终结果**。必须精简为单通道极简 Gray_2x。

### 案例 3：括号进度字形混淆 (FAIL-03)
- **现状**：羁绊卡片名称右上角包含实机等级进度（例如 `(0/4)`, `(1/3)`）。PaddleOCR 将整个文本行连同括号一起识别，如将 `箭术(1/3)` 识别为 `新术(13)`。
- **决策结论**：
  1. 紧缩 name ROI 宽度，避开右侧括号区域；
  2. 文本正则预处理强行剥离 `r"[\(\[（【]\s*\d+\s*/\s*\d+\s*[\)\]）】]"`；
  3. 在 `choice_lexicon.json` 别名表中加入 OCR 高频字形混淆（如 `新术` -> `箭术`, `已馨` -> `已隐`）。
